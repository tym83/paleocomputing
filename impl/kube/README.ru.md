# Kube: управляющий слой Kubernetes на Обероне

Kube — минимальный управляющий слой Kubernetes, написанный на Обероне-07 и
собираемый компилятором Оберона на машине Вирта. Он не подражает внешнему виду
Kubernetes, а воспроизводит идею, на которой тот держится: вы объявляете
желаемое состояние, а независимые контроллеры раз за разом сравнивают его с
существующим и убирают разницу. Вся история, включая то, как Kube запустился в
Cozystack, рассказана в выпуске [`15-episode-kube.ru.md`](../../15-episode-kube.ru.md).

## Соответствие

Есть хранилище объектов с Deployment, ReplicaSet и Pod и три контроллера. Они
работают как фоновые задачи `Oberon.Task` в том же кольце, что и сборщик мусора
системы, и `Oberon.Loop` вызывает их между действиями пользователя, как это
делал бы kube-controller-manager.

| Kubernetes | Оберон |
|---|---|
| etcd | массив записей `store` |
| API и kubectl | команды по среднему щелчку: `Kube.Apply`, `Kube.Get`, `Kube.DeletePod` |
| контроллер деплойментов | `ctlDeploy`: один ReplicaSet на Deployment, с его числом реплик и образом |
| контроллер репликасетов | `ctlRS`: число подов равно `replicas` |
| планировщик | `ctlNode`: привязывает под к наименее загруженному узлу в состоянии Ready и отвязывает поды узла, ушедшего в NotReady, чтобы они переехали |
| kubelet | `KubeNet` на машине-узле: запускает то, что назначила управляющая машина, и сообщает об этом в сигнале жизни |
| контроллер жизненного цикла узлов | `Kube.Expire`: узел, молчащий три секунды, уходит в NotReady |
| ownerReferences | поле `owner`: под принадлежит репликасету, репликасет деплойменту |
| узлы | другие машины с Обероном в радиосети Вирта или три локальных узла для одной машины |

## Запуск

```sh
cd impl
kube/check.sh     # Norebo без экрана: компиляция, три реплики, удаление пода, масштаб до одной
kube/system.sh    # настоящая система на RTL: build/kube/kube_rtl.png, одна-две минуты
```

В Norebo нет `Oberon.Loop`, поэтому `check.sh` крутит цикл вручную. В
`system.sh` система сама компилирует `Kube.Mod`, а согласование выполняют
фоновые задачи; результат в [`kube-in-oberon.png`](kube-in-oberon.png):

```
deployment web  replicas=3  image=nginx
  replicaset web-rs  desired=3
    pod web-rs-0 @node-a Running
    pod web-rs-1 @node-b Running
    pod web-rs-2 @node-c Running
```

В живой системе команды запускаются средней кнопкой (через VNC это Alt с левым
щелчком):

| команда | |
|---|---|
| `Kube.Start` | поставить три контроллера и ждать узлов по радио |
| `Kube.Start local` | то же самое с тремя локальными узлами, для одной машины |
| `Kube.Apply name N image` | объявить деплоймент или изменить число его реплик |
| `Kube.Get` | напечатать дерево объектов в журнал |
| `Kube.DeletePod "name"` | удалить под; следующий такт создаст его заново под новым именем |
| `Kube.Stop` | снять контроллеры, объекты останутся |
| `Kube.Run N` | прокрутить N тактов вручную, для Norebo |
| `Kube.Save [file]` | записать в файл то, что печатает `Kube.Get`, по умолчанию в `Kube.State` |

Имя пода пишется в кавычках, потому что текстовый сканер Оберона заканчивает имя
на дефисе.

## Настоящие узлы по радио

Кластер состоит из нескольких машин с Обероном в одном эфире (приложение
`OberonAir` в каталоге): одна работает управляющей, остальные служат узлами.
Они общаются через радиосеть Вирта, драйвер nRF24L01+ `SCC` из Project Oberon.
Машина QEMU моделирует этот радиомодуль, а ретранслятор переносит пакеты между
виртуальными машинами.

На управляющей машине:

```
Kube.Start
KubeNet.Serve
Kube.Apply web 3 nginx ~
```

На каждом узле:

```
KubeNet.Join node-a
```

Протокол состоит из двух сообщений, и каждое занимает один радиопакет, который
получают все. Kubelet раз в секунду рассылает сигнал жизни со списком подов,
которые он выполняет. Управляющая машина раз в секунду посылает каждому узлу в
состоянии Ready список подов, привязанных к нему. Обе стороны, как и их
прототипы в Kubernetes, сверяют состояние, а не реагируют на события: узел
выполняет ровно то, что было в последнем списке, поэтому потерянный пакет
исправит следующий. Узел, молчавший три секунды, уходит в NotReady, и
планировщик переносит его поды на оставшиеся узлы. Сообщения намеренно
укладываются в один пакет. У радио нет защиты от коллизий, и если две станции
одновременно передают длинные сообщения, их части перемешаются у получателей.

В радиосети под обозначается номером в один байт, а в сигнал жизни помещается
до 15 номеров, так что на одном узле может работать до 15 подов. Деплоймент
стоит применять, когда его узлы уже в Ready: как и настоящий планировщик, Kube
не переносит работающие поды на узел, подключившийся позже.

`qemu/test/kube_radio_check.py` проверяет это на трёх машинах и
ретрансляторе. Оба узла в Ready, три пода распределены между ними, затем один
узел выключается, уходит в NotReady, и все три пода работают на оставшемся.

`Net`, `Kube` и `KubeNet` скомпилированы на системный диск образа `oberon-run`
(`tools/install_modules.py`), так что в `OberonVM` их можно запускать сразу,
ничего не набирая.

## В Cozystack

Kube работает и внутри `OberonVM` из каталога. Пока модулей не было на
системном диске, его набирали в редакторе через VNC, сохраняли, компилировали
внутри системы командой `ORP.Compile Kube.Mod/s` и запускали командами выше.
Чтобы до этого дойти, пришлось исправить клавиатуру и диск виртуальной машины
([находка 86](../docs/FINDING-86-qemu-keyboard-byte-load.ru.md)).
