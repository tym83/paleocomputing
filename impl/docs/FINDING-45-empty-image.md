# Finding 45. The image is published, but there is nothing in it to work with

The lab's serving image was built and published **without the machine**. It
contained the page and nothing else:

```
lab.html    present, 12019 bytes
oberon.dsk  ❌ MISSING
risc5.wasm  ❌ MISSING
risc5.js    ❌ MISSING
prom_sd.mem ❌ MISSING
```

The page was served correctly, but there was nothing on it to boot: the browser
had nothing to load.

## Why it went unnoticed

The cluster run checked that the page arrived: `HTTP 200, 12019 bytes`.
Exactly the number that is visible now as well. **The check looked at the shape
of the response, not at behavior**, and therefore confirmed success.

This is the same signature as in Finding 35: the release succeeded, the
application is dead.

## Two causes, both silent

**Build products in `.gitignore`.** `risc5.js`, `risc5.wasm`, `prom_sd.mem`
and `oberon.dsk` are built from sources that are in the repository. Locally the
files sit next to each other, and `COPY web/` picks them up. In the build they
are absent, and the same line copies what is not there, silently.

**The case trap in `.gitignore`.** The line `/norebo` in `ext/norebo/.gitignore`
was written against the built binary. But on case-insensitive file systems
(macOS by default), git compares names without regard to case, and the line
swallows the `Norebo/` directory with the entire language library.

41 library files never made it into the repository. The same trap is already
described in our Makefile, where it made a target coincide with a directory,
and it fired a second time in a different place.

## A third cause, found while fixing

Building the machine inside the image did not work on the first try, and it
exposed a bug in our own Makefile.

The list of files generated by verilator was taken via
`$(wildcard build/obj_wasm/*.cpp)`. **GNU make caches directory contents for
the whole run**: it reads `build/obj_wasm` before verilator writes there, and
the list stays empty. `VRISC5.cpp` does not get into the build, and linking
fails on `eval_step`.

Locally this is invisible: the files are left over from the previous run, and
the cache sees them. It shows up only on a **clean** build, that is, everywhere
except the developer's machine.

The list is now produced by the shell, not by make.

Along the way it turned out that the verilator version must match the one the
model was verified with: the headers are compiled together with the model, and
the distribution's version has headers that do not build for wasm.

## What was done

**The machine is built inside the image itself.** Verilator and emscripten are
installed in a separate stage, and `make web` generates what was missing. All
sources are in the repository, so the image is now self-contained.

**Content check after publishing.** The build looks inside the published image
and makes sure the required files are present and non-empty:

```
docker run --rm --entrypoint sh "$ref" -c "test -s $dir/$f"
```

The rule that follows: **check not that the build passed, but that the artifact
contains something to work with**. A successful build says nothing about the
contents if it copies something that is not there.
