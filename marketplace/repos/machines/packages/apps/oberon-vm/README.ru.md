# Oberon VM — RISC5 Вирта как виртуальная машина

Целая архитектура, подключённая к кластеру снаружи. Машина, которая здесь
запускается, — не эмулятор, изображающий железо Оберона, а цель QEMU, собранная
по описанию схемы самого Вирта и сверенная с ним инструкция за инструкцией.

## Что вы получаете

Project Oberon 1986 года, загружающийся со своего диска: журнал, окно
инструментов, редактор, компилятор. Целая система — процессор, компилятор,
операционная система, окна — примерно в шести тысячах строк.

## Три кнопки мыши

Оберону нужны все три, а у ноутбука средней нет. Машина переводит сочетания с
клавишами-модификаторами и первые полминуты пишет об этом на своём экране:

| удерживайте | и щёлкните | получится |
|---|---|---|
| Alt | левой | средняя кнопка — **запускает команды** |
| Ctrl | левой | правая кнопка |
| Shift | левой | обе сразу — *interclick* |

Interclick ставит второй угол прямоугольника. Без него часть системы
недоступна.

## Что должен дать кластер

Две вещи, которые один раз настраивает тот, кто ведёт кластер, — тенант их
задать не может:

1. **Feature gate `Sidecar`** в ресурсе KubeVirt. Без него хук, переписывающий
   описание домена, не запускается.
2. **Образ `virt-launcher`, libvirt которого знает архитектуру.** libvirt
   спрашивает у эмулятора, какая у него архитектура, а не верит описанию
   домена, поэтому архитектуру нужно вкомпилировать. Правка — около десяти
   строк в пяти таблицах; образ публикуется вместе с этим каталогом.

Этот образ несёт всё семейство машин. Кластер подключается один раз, и дальше
любой тенант ставит любую машину из каталога — примерно как пакет драйвера.
Платформенный компонент `kubevirt-paleo-launcher` (репозиторий `platform`)
держит этот образ в соответствии с версией KubeVirt кластера.

## Как это работает

`OnDefineDomain` — поддерживаемая точка расширения KubeVirt: сайдкар получает
сгенерированный KubeVirt домен и возвращает переписанный. Форк KubeVirt не
нужен, и образ сайдкара тоже — стандартная прослойка запускает скрипт, который
этот чарт передаёт через ConfigMap.

Эмулятор живёт в образе запускателя; PROM и образ системы приходят на том,
общий с контейнером, где работает libvirt. PROM обновляется с каждым выпуском;
системный диск копируется один раз и дальше принадлежит пользователю.

Машина — это `VirtualMachine`, поэтому её можно останавливать, запускать и
перезапускать из панели. Всё, что делает её Обероном, — данные в
`machine.yaml`: шаблоны и хук общие для всех машин каталога
(`packages/library/retro-machine`).

## Кластер Kube из формы

На системном диске лежит Kube, управляющая часть Kubernetes на Обероне, и
KubeNet, который передаёт её по радио Вирта. Несколько машин в одном
`OberonAir` сами собираются в кластер, если в форме сказано, кто из них кто:

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: OberonVM
metadata:
  name: plane
spec:
  air: lab
  kubeRole: plane
  kubeKey: 00c0ffee00c0ffee
  commands: Kube.Apply web 4 Ticker
---
apiVersion: apps.cozystack.io/v1alpha1
kind: OberonVM
metadata:
  name: node-a
spec:
  air: lab
  kubeRole: node
  kubeNode: node-a
  kubeKey: 00c0ffee00c0ffee
```

При старте управляющая машина выполняет `Kube.Start` и `KubeNet.Serve`, узел —
`KubeNet.Join`; набирать ничего не нужно. Команды выполняются при каждом
старте, поэтому с `Kube.Apply` источником истины служат они: деплоймент,
изменённый через VNC, при следующем перезапуске вернётся к ним. `Kube.Ensure`
создаёт деплоймент, только если его ещё нет, и сохраняет то, что изменили на
управляющей машине. Управляющая машина хранит объекты на
своём диске и после перезапуска возвращается с ними. Новые деплойменты
применяются на ней через VNC, например `Kube.Apply web 6 Ticker2`, и `web`
выкатывается на вторую версию по одному поду.

| поле | |
|---|---|
| `kubeRole` | `plane` или `node`; нужен `air` |
| `kubeCluster` | имя кластера до 8 символов, по умолчанию `kube`; в одном эфире может быть несколько кластеров |
| `kubeNode` | имя узла до 6 символов |
| `kubeKey` | до 16 шестнадцатеричных цифр, один и тот же на всех машинах кластера: каждое сообщение в эфире подписано им, и узел слушается только подписанных сообщений своего кластера |
| `commands` | любые команды Оберона при старте через `;`, после команд роли Kube |

Образ пода — это имя модуля Оберона на узле: попробовать можно `Ticker` и
`Ticker2`. Kubelet загружает модуль и вызывает его команду `Start`; под, чьего
модуля нет, остаётся Pending, как под, образ которого не скачивается. На узле
работает до 10 подов — столько помещается в один радиопакет.

Как это устроено, что измерено и что ломалось по дороге, — в
`impl/kube/README.ru.md` репозитория.

## Команды при старте

`commands` нужны не только для Kube. Текст приходит в машину по
последовательной линии (приём RS232) с момента включения, и `Boot.Mod`,
вызываемый в конце запуска системы, выполняет каждую команду, будто по ней
щёлкнули: cloud-init для Оберона. Всего до 240 печатных символов.
