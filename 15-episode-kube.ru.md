# Выпуск: Kube, управляющий слой Kubernetes внутри Оберона

Статус: работает. Kube запускается в командной строке Norebo, в настоящей системе
Оберон на RTL машины Вирта, в нашей цели QEMU и в `OberonVM` в Cozystack. Код
лежит в [`impl/kube/`](impl/kube/), а то, что нашлось по дороге, описано в
[находке 86](impl/docs/FINDING-86-qemu-keyboard-byte-load.ru.md).

## Зачем это

Kubernetes обычно объясняют через масштаб: тысячи узлов, API-сервер, etcd,
десятки контроллеров, миллионы строк на Go. Но за всем этим стоит одна небольшая
идея. Системе не говорят, что делать. Ей записывают, что должно существовать, а
набор независимых циклов раз за разом сравнивает существующее с желаемым и
понемногу убирает разницу. Если под умер, никому не нужно это заметить и
перезапустить его: следующий проход цикла просто увидит, что подов на один
меньше, и создаст недостающий.

Для этой идеи кластер не нужен. Она помещается в один модуль примерно из трёхсот
строк и естественно ложится на Оберон, систему, которую один человек может
прочитать целиком, от процессора и выше, за несколько вечеров. Kube переносит
ядро Kubernetes на эту машину и собирается её собственным компилятором, так что
весь путь от «хочу три реплики» до «три пода работают» можно пройти строка за
строкой, и ничего не спрятано под фреймворком.

Заодно это проверка платформы. Программа в десять тысяч символов, которую
набирают в системе, сохраняют, компилируют и запускают, стала первой серьёзной
работой для клавиатуры и диска нашей виртуальной машины. У обоих нашлись
дефекты, до которых загрузка системы никогда не доходила.

## Что такое Kube

Kube — минимальный управляющий слой на Обероне-07
([`impl/kube/Kube.Mod`](impl/kube/Kube.Mod)). В нём есть хранилище объектов трёх
видов (Deployment, ReplicaSet и Pod) и три контроллера.

* **Контроллер деплойментов** держит ровно один ReplicaSet на каждый Deployment
  и переносит в него желаемое число реплик и образ.
* **Контроллер репликасетов** считает поды, которыми владеет ReplicaSet, и
  создаёт или удаляет их, пока число не сравняется с `replicas`.
* **Контроллер узлов** делает работу планировщика и kubelet: ставит каждый
  нераспределённый под на наименее загруженный узел, а потом переводит его из
  Pending в Running.

Узлы `node-a`, `node-b` и `node-c` смоделированы. Это просто имена, и под
«работает» на узле потому, что контроллер узлов записал в него имя узла. Образ
тоже всего лишь метка. Ничего не исполняется; настоящий здесь цикл управления,
то есть та часть Kubernetes, которая и делает его Kubernetes.

## Как это ложится на Оберон

Соответствие оказалось близким, потому что в Обероне уже есть то единственное,
что нужно управляющему слою: центральный цикл, который вызывает фоновую работу.

| Kubernetes | Оберон |
|---|---|
| etcd, хранилище объектов | массив записей `store` на 256 мест |
| API и kubectl | команды, которые запускаются средним щелчком: `Kube.Apply`, `Kube.Get`, `Kube.DeletePod` |
| цикл согласования контроллера | `Oberon.Task` в фоновом кольце, рядом со сборщиком мусора системы |
| kube-controller-manager | `Oberon.Loop`, который вызывает задачи кольца в промежутках между действиями пользователя |
| ownerReferences | поле `owner`: подом владеет ReplicaSet, ReplicaSet принадлежит Deployment |
| узлы кластера | смоделированные `node-a/b/c` |

`Kube.Start` ставит три контроллера как три отдельные задачи с периодом 50 мс в
то же кольцо, где работает сборщик мусора системы. С этого момента
`Oberon.Loop` вызывает их всякий раз, когда пользователь не печатает и не
щёлкает, точно так же, как kube-controller-manager гоняет свои контроллеры в
настоящем кластере. Контроллеры друг друга не вызывают. Каждый смотрит только на
объекты своего вида и меняет только то, чем владеет, а результат одного прохода
становится входом для другого контроллера на его следующем проходе. Именно так
сотрудничают контроллеры Kubernetes: через общее состояние, а не через сообщения.

Каждый контроллер работает по уровню, а не по событию. Он не реагирует на
«под удалили», он смотрит на текущее состояние и исправляет его. Поэтому
удалённый под возвращается без всякого особого кода для удаления. Контроллер
репликасетов не знает, что что-то удалили; он видит два пода там, где нужно три.

## Как запустить

В командной строке, в Norebo, эмуляторе RISC5 Вирта без экрана. Там нет
`Oberon.Loop`, поэтому демонстрация крутит цикл вручную:

```sh
cd impl
kube/check.sh
```

Скрипт компилирует `Kube.Mod` компилятором Оберона и запускает `Kube.Demo`.
Демонстрация объявляет деплоймент на три реплики, удаляет под, а потом уменьшает
деплоймент до одной реплики:

```
== apply deployment web, replicas=3 ==
deployment web  replicas=3  image=nginx
  replicaset web-rs  desired=3
    pod web-rs-0 @node-a Running
    pod web-rs-1 @node-b Running
    pod web-rs-2 @node-c Running
== delete pod web-rs-0, reconcile ==
deployment web  replicas=3  image=nginx
  replicaset web-rs  desired=3
    pod web-rs-3 @node-a Running
    pod web-rs-1 @node-b Running
    pod web-rs-2 @node-c Running
== scale deployment web to 1, reconcile ==
deployment web  replicas=1  image=nginx
  replicaset web-rs  desired=1
    pod web-rs-2 @node-c Running
```

Замена получает новое имя `web-rs-3` и попадает на `node-a`, потому что после
удаления этот узел загружен меньше всех.

В настоящей системе Оберон, с окнами, на RTL машины Вирта:

```sh
cd impl
kube/system.sh        # build/kube/kube_rtl.png, одна-две минуты
```

Здесь система сама компилирует `Kube.Mod`, а согласование выполняют фоновые
задачи, а не скрипт. Снимок экрана лежит в
[`impl/kube/kube-in-oberon.png`](impl/kube/kube-in-oberon.png).

В живой системе команды запускаются средней кнопкой мыши (на двухкнопочной мыши
и через VNC это Alt с левым щелчком):

| команда | что делает |
|---|---|
| `Kube.Start` | ставит три контроллера |
| `Kube.Apply web 3 nginx` | объявляет деплоймент или меняет число реплик у существующего |
| `Kube.Get` | печатает в журнал дерево деплойментов, репликасетов и подов |
| `Kube.DeletePod "web-rs-0"` | удаляет под; следующий такт создаёт его заново под новым именем |
| `Kube.Stop` | снимает контроллеры, объекты остаются |
| `Kube.Run 5` | прокручивает цикл пять раз вручную, для Norebo |

Имя пода в `DeletePod` пишется в кавычках, потому что текстовый сканер Оберона
заканчивает имя на дефисе. Без кавычек `Kube.DeletePod web-rs-3` искал под с
именем `web`, не находил его и молча ничего не делал. Это нашлось при проверке в
QEMU и исправлено.

## Что проверено

| где | что произошло |
|---|---|
| Norebo (`kube/check.sh`) | три реплики, удалённый под пересоздан как `web-rs-3`, масштаб уменьшен до одной |
| RTL машины Вирта (`kube/system.sh`) | система сама компилирует `Kube.Mod`, ставятся три контроллера, работают три пода; `Kube.DeletePod "web-rs-0"` удаляет под, и следующий такт создаёт его заново как `web-rs-3` |
| наша цель QEMU, локально | текст модуля, 10 212 символов, набран в редакторе Оберона через события клавиатуры, сохранён, скомпилирован внутри системы и запущен; масштабирование до одной и до четырёх реплик согласовалось, новые поды встали на наименее загруженные узлы |
| Cozystack, тенант-песочница на кластере воркшопа | `OberonVM` из каталога; модуль набран через VNC (`virtctl vnc`), сохранён и скомпилирован внутри системы; три контроллера, три пода в состоянии Running |

Последняя строка и есть смысл всего упражнения: управляющий слой Kubernetes на
языке 1986 года, собранный собственным компилятором этого языка, работает в
виртуальной машине, которой в свою очередь управляет Kubernetes.

## Дорога в Cozystack

На RTL модуль попадает на диск скриптом, который вписывает его прямо в образ
диска. В облачной машине так нельзя: единственный вход туда — клавиатура через
VNC. Значит, модуль нужно было набрать, и набор десяти тысяч символов на машине,
которую до сих пор только загружали и щёлкали мышью, вскрыл пять проблем. Все
они описаны в [находке 86](impl/docs/FINDING-86-qemu-keyboard-byte-load.ru.md) и
исправлены в PR #67.

**1. Первое же нажатие клавиши вешало машину.** В QEMU к каждому устройству
обращаются через порты ввода-вывода, и наша цель объявляла, что её порты
принимают только целые 32-битные слова. Драйвер клавиатуры Оберона при этом
читает код клавиши однобайтовой загрузкой, потому что код и есть байт. QEMU
отвергал такое обращение, клавиша не уходила из очереди, флаг «есть нажатие»
оставался поднятым, и система бесконечно читала одно и то же нажатие. На
настоящей плате младшие биты адреса не учитываются и чтение байта работает,
поэтому пошаговая сверка с RTL этого не поймала: при загрузке клавиатуру никто
не читает. Теперь порты принимают обращения любого размера.

**2. Быстрый ввод терялся.** У контроллера клавиатуры Вирта очередь на 16 байт,
и человеку, который печатает руками, этого хватает с запасом. Программа, которая
шлёт клавиши через VNC или через управляющий интерфейс QEMU, гораздо быстрее, а
одно нажатие с Shift занимает в очереди шесть байт. При 680 символах в секунду
дошло только 5359 символов из 10 212. Теперь очередь на 4096 байт, и нажатие
кладётся в неё либо целиком, либо никак: половина нажатия, например отпускание
без своего префикса, оставила бы систему в уверенности, что Shift всё ещё
зажат. Но большая очередь только сглаживает всплески. Машина обрабатывает
нажатия медленнее, чем их может слать скрипт, поэтому отправитель должен сам
сдерживать темп; с паузой 5 мс между символами не потерялось ни одного.

**3. Редактор теряет нажатия у нижнего края окна.** Когда курсор доходит до
последней видимой строки окна, редактор Оберона теряет часть нажатий и склеивает
строки, всегда на одной и той же строке и при любой скорости. Так ведёт себя сам
редактор, QEMU тут ни при чём. Обходной путь в том, чтобы вставлять строки в
обратном порядке в начало текста: тогда курсор не спускается к краю.

**4. Песочница запускала старый лаунчер.** Перед выпуском изменения проверяются
в песочнице на образах с тегом `dev`. Этот тег перезаписывает каждая тестовая
сборка, а узлы кластера скачивают образы с политикой `IfNotPresent`: узел, у
которого образ с таким тегом уже есть, больше не спрашивает реестр. Поэтому
песочница продолжала работать на эмуляторе из прежней сборки, без исправления
клавиатуры, и казалось, что исправление не работает. Теперь опубликованная
таблица лаунчеров и паспорт машины ссылаются на образы по дайджесту, то есть по
хешу точного содержимого, и узел скачивает ровно ту сборку, которая была
опубликована.

**5. Сохранённый файл бесследно пропадал.** Диском облачной машины был
поставляемый образ размером около 1 МБ. Файловая система Оберона кладёт новые
файлы в секторы за концом этого образа, а QEMU отказывается писать за конец
сырого файла диска. Поэтому файл побольше при сохранении терялся, а запись о нём
в каталоге указывала в никуда. Теперь паспорт машины объявляет размер диска,
8 МиБ, а задание, которое готовит том, дополняет диск нулями до этого размера,
не трогая того, что на нём уже записано. Диск, созданный прежним выпуском,
увеличивается так же.

Раньше ничего из этого не было видно, потому что на машине никто не работал.
Клавиатуру проверяли несколькими буквами, а с диска только читали.
