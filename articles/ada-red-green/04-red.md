# Экскурсия по RED

На первый взгляд RED выглядит как Паскаль, который долго посещал качалку. Вот кусок пакета матричной арифметики из приложения к обоснованию, примеры для которого писали Пол Абрахамс, Брюс Кноб, Дэвид Левин и другие. Константы я подставил, а комментарии убрал. Смотрите прежде всего на типы и на заголовок функции:

```
CAPSULE matrix_vector_package EXPORTS ALL;
CONST maxdim := 100;
ABBREV mvfloat : FLOAT(6, -1.0E99 .. 1.0E99);
ABBREV dim : INT(2 .. maxdim);
TYPE matrix(m : dim, n : dim) : ARRAY INT(1 .. m), INT(1 .. n) OF mvfloat;
TYPE vector(n : dim) : ARRAY INT(1 .. n) OF mvfloat;

FUNC *(READONLY b : matrix, READONLY c : vector) => vector(b.m);
    ASSERT b.n = c.n;
    VAR a : vector(b.m);
    FOR i : INT(1 .. b.m) REPEAT
        a(i) := 0.0;
        FOR j : INT(1 .. b.n) REPEAT
            a(i) := a(i) + b(i,j) * c(j);
        END REPEAT;
    END REPEAT;
    RETURN a;
END FUNC *;
```

Но если присмотреться, в этих полутора десятках строк уже много того, что придёт в мейнстрим гораздо позже. `ABBREV` здесь просто даёт подтипу короткое имя, а `FLOAT(6, …)` задаёт вещественный тип с точностью 6 и заданным диапазоном. Размерности живут прямо в типе: `vector(n)` — тип с параметром, а `b.m` и `c.n` читаются как обычные атрибуты значения. Поэтому и тип результата вычисляется из аргументов, и функция заранее обещает вернуть `vector(b.m)`. Оператор `*` перегружен по типам операндов, так что одним знаком умножают число на вектор, матрицу на число, матрицу на вектор и матрицу на матрицу. А дальше в пакете векторное произведение объявлено как `*` для `vector(3)`, то есть ограничение на размерность записано прямо в типе параметра, и вызов с вектором другой длины поднимет исключение подтипа. В Rust такое ограничение записали бы через const generics, `Vector<3>`. Кроме того, тут есть `ASSERT` прямо в теле функции как часть языка.

Дальше я пройдусь по тому, что мне показалось в RED самым интересным. Почти всё это не пересказ руководства, а то, обо что я споткнулся сам, когда писал (не своими руками, да) на RED компилятор, операционную систему и Kubernetes.

## Капсулы и абстрактные типы без слова private

Модуль в RED называется капсулой. Капсула экспортирует ровно то, что перечислено после `EXPORTS`, а тот, кто ею пользуется, явно открывает то, что ему нужно, через `EXPOSE`:

```
CAPSULE stackcap EXPORTS stack, init, push, pop;
   TYPE stack : RECORD[top : INT(0 .. 100), elem : ARRAY INT(1 .. 100) OF INT];
   ...
END CAPSULE stackcap;

EXPOSE stack, push, pop FROM stackcap;
```

В Аде абстрактный тип создаётся секцией `private` в спецификации пакета. В RED нет никакой секции, зато есть правило, которое я сначала пропустил, а потом сам же на нём споткнулся: когда капсула экспортирует тип, она не экспортирует ни выбор его компонент, ни присваивание. Снаружи переменную типа `stack` можно объявить и передать в `push`, но написать `s.top := 0` нельзя. Хотите открыть внутренности, проще всего экспортировать всё через `EXPORTS ALL`. То есть абстрактность типа определяется не тем, как он объявлен, а тем, что из капсулы выпущено наружу. Если подумать, это очень честная модель: тип сам по себе ничего не прячет, прячет граница модуля.

## Закрытые области и IMPORTS

Это правило оказалось самым ощутимым в повседневной работе. Процедура в RED — закрытая область: константы, типы и другие процедуры снаружи она видит, а переменные нет, пока явно их не импортирует:

```
VAR hits : INT := 0;
VAR limit : INT := 3;
PROC hit IMPORTS hits, READONLY limit;
   IF hits < limit THEN
      hits := hits + 1;
   END IF;
END PROC hit;
```

Переменную можно импортировать и только для чтения, как `limit` в примере. По сути, это тот же список захвата, что у лямбд в C++, только обязательный и для всех процедур. Для языка, задуманного под сопровождение огромных программ десятилетиями, это разумно: по заголовку процедуры сразу видно, какое состояние она может испортить.

Рядом стоит различие нормальных и ненормальных функций. Нормальная функция зависит только от аргументов, и транслятор имеет право выбросить повторный вызов с теми же аргументами. Если результат функции зависит не только от аргументов, например она читает внешние переменные, перед ней надо написать `ABNORMAL`. Нормальной функции разрешено менять разве что собственные переменные своей капсулы, например счётчик вызовов или мемо-таблицу. Слово выглядит смешно, но идея близка к тому, что сейчас называют чистыми функциями.

Параметры передаются четырьмя способами: `CONST` копирует, `READONLY` передаёт по ссылке без права изменения, `VAR` по ссылке с изменением, а `OUT` — это локальная переменная, значение которой переходит в фактический параметр, только если процедура завершилась нормально. Если процедура закончилась исключением, переменная вызывающего остаётся такой, какой была. Зачем различать чтение копией и чтение по ссылке, красная команда объясняет отдельно. Оставить способ на усмотрение транслятора нельзя, потому что тогда поведение программы зависит от реализации, а всегда копировать слишком дорого для больших объектов.

## Выход из цикла по имени

Мелочь, которая мне очень понравилась. `EXIT` в RED обязан назвать оператор, из которого выходит:

```
outer WHILE p /= NIL REPEAT
   ...
   IF found THEN
      EXIT outer;
   END IF;
END REPEAT outer;
```

Обоснование такого решения простое: если бы `EXIT` выходил из ближайшего цикла, то вставка нового цикла вокруг него молча изменила бы смысл программы. А сам я видел этот баг в продакшене больше раз, чем хотелось бы.

## Почтовые ящики, WAIT и REGION

Главное отличие RED от будущей Ады — параллельность, и тут нужно небольшое отступление для тех, кто на Аде не писал (то есть почти для всех). Задачей (task) в обоих языках называется то, что сегодня назвали бы потоком: кусок программы, который выполняется одновременно с остальными. Вопрос в том, как задачи договариваются между собой. В Аде, а до неё в зелёном языке, единственный способ сделать это — рандеву. У задачи-сервера есть входы, entry, похожие на процедуры. Клиент вызывает вход и ждёт, сервер в своём коде доходит до оператора `accept` для этого входа и тоже ждёт, и когда оба на месте, выполняется тело `accept`, после чего каждый идёт дальше своей дорогой. Это встреча, отсюда и название. RED устроен иначе: задачи обмениваются сообщениями через почтовые ящики, то есть очереди сообщений между задачами внутри программы, а общие данные защищают критическими секциями:

```
VAR m : MAILBOX[msg](3);         % ящик на три сообщения
VAR d : DATA_LOCK;

TASK consumer IMPORTS m;
   VAR data : msg;
   WHILE TRUE REPEAT
      RECEIVE(m, data);
      ...
   END REPEAT;
END TASK consumer;

VAR c : ACT;
CREATE consumer NAMED c;
SEND(m, x);

REGION d DO
   shared := shared + 1;          % замок отпустят, как бы ни закончилось тело
END REGION;
```

Ящик типизирован и ограничен. Ящик размера ноль — это рандеву: отправитель не может обогнать получателя. Оператор `WAIT` ждёт первого из нескольких событий, приёма из любого ящика, отправки или тайм-аута:

```
WAIT
   WHEN RECEIVE(ports(me), m) => handle(m);
   WHEN DELAY(35) => take_over;
END WAIT;
```

И здесь есть деталь, по которой видно, как тщательно продумывали язык. `SEND` в ящик нулевого размера внутри `WAIT` запрещён: такая попытка поднимает исключение `X_EMPTY_MAILBOX`. Почему? Потому что иначе задачи, которые ждут друг у друга отправки в нулевые ящики, могут встать в круговое ожидание, а предотвратить его можно только глобальным планированием.

`REGION` захватывает замок данных и гарантированно отпускает его, как бы ни закончилось тело: обычным образом, по исключению, выходом из цикла или возвратом из процедуры. В Аде 83 ничего подобного нет, и замок в ней делается отдельной задачей с двумя входами, которая при исключении между захватом и освобождением так и остаётся захваченной. Об этом подробнее в главе об Аде 83.

Задачи запускаются явно, `CREATE задача NAMED переменная`, и у каждой активации есть имя, переменная типа `ACT`. Через неё можно спросить, жива ли задача, поменять ей приоритет, дождаться её завершения или убить через `EXTERMINATE`. Встроенный планировщик приоритетный: первой работает задача с более высоким приоритетом, а при равных та, что дольше ждёт.

## Свой планировщик

На нижнем уровне языка (это описано в четырнадцатой главе руководства) системный программист может описать собственный планировщик и собственные механизмы синхронизации, потому что язык отдаёт ему операции самого планировщика: приостановить активацию, дождаться сигнала, сделать участок кода критическим, чтобы его не вытеснили и не убили на полпути. Встроенные почтовые ящики, замки и `WAIT` описаны в той же главе как частные случаи, собранные из этих операций, и руководство показывает это на примерах: планировщик с круговой очередью, мониторы Хоара поверх замков данных и даже сам `MAILBOX`, определённый средствами языка. В моём компиляторе все эти примеры работают. Сам факт, что язык 1979 года предлагал пользователю писать планировщики, а не только пользоваться инструментарием, для меня очень показателен.

## Обобщения, которые создаются сами

Обобщённая процедура в RED выглядит так:

```
GENERIC t : TYPE NEEDS :=(t, t)
   PROC swap(VAR a, b : t);
      CONST c := a;
      a := b;
      b := c;
   END PROC swap;

swap(i, j);       % i и j целые
swap(s, r);       % s и r строки
```

Обратите внимание, чего здесь нет. В Аде нужно сначала явно создать экземпляр, `procedure SWAP_INT is new SWAP(INTEGER)`, и только потом вызывать. В RED оператора создания экземпляра нет вообще: каждый вызов сам сообщает транслятору, какие нужны типы, а транслятор создаёт экземпляр или берёт уже созданный. Так потом заработают шаблоны C++, только в RED это было реализовано на одиннадцать лет раньше. А список `NEEDS` перечисляет, какие операции должны быть у типа-параметра (здесь присваивание). В C++ то же самое появилось лишь в 2020 году под именем концептов. Мой компилятор проверяет этот список в каждой точке вызова: если нужной операции там нет или у неё не тот заголовок, вызов не переводится. Параметрами обобщения могут быть типы, значения, процедуры и даже задачи. В решении контрольного задания о планировщике красная команда передаёт задачу параметром в обобщённую задачу-обёртку, которая запускает её по расписанию.

## Строки, которые помнят свою длину

Строковый тип в RED — это `STRING[ASCII](n)`, и длина фиксирована для каждого объекта. Присвоить строку другой длины нельзя, это ошибка подтипа. Для текста переменной длины нужен указательный тип с параметром, и в руководстве есть как раз такой пример, таблица символов:

```
TYPE sym : PTR (len : INT) STRING[ASCII](len);
ALLOC s.syms(s.top) PTR (val.LEN) := val;
```

`ALLOC` создаёт динамическую строку ровно той длины, что у `val`, и кладёт указатель на неё в таблицу. Компилятор RED, написанный на RED, хранит все имена и куски сгенерированного кода именно так. А символы ASCII в RED — это значения перечисления с именами, и строчная буква a записывается как `'L_A`, апостроф как `'APOS`, кавычка как `'QUOTE`. Кавычку внутри строкового литерала написать нельзя вообще, только склеить строку с символом. В исходнике компилятора, который генерирует C, это выглядит забавно: `"rt_str(" & q & "TRUE" & q & ", 4)"`, где `q` — функция, возвращающая кавычку.

## FREE, который отказывается освобождать

И последнее, что меня впечатлило в руководстве. Динамическая переменная в RED живёт, пока на неё есть ссылки, то есть по умолчанию язык рассчитан на сборку мусора. Но для тех, кто не может себе её позволить, есть процедура `FREE`. Если на освобождаемую переменную есть другие указатели, `FREE` не освобождает её, а поднимает исключение `X_FREE`. Висячий указатель становится невозможен в принципе, а саму проверку, если она слишком дорога, можно отключить прагмой, то есть указанием транслятору прямо в тексте программы: `PRAG(SUPPRESS(X_FREE))`. И всё это в 1979 году. В моём компиляторе `FREE` перед освобождением обходит всю достижимую память: глобальные переменные, кадры работающих подпрограмм каждой задачи, динамические переменные и буферы почтовых ящиков. Программа без `FREE` за это ничего не платит.
